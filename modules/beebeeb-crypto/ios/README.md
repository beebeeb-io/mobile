# beebeeb-crypto iOS bindings

Swift bindings to the Rust `beebeeb-core` crate, generated by `uniffi-bindgen`.

## Canonical location

`modules/beebeeb-crypto/ios/beebeeb_uniffi.swift` is the **single source of
truth** for the Swift bindings. As of task 0431,
`ios/Beebeeb/beebeeb_uniffi.swift` is a symlink that points here, so the
Xcode native targets (Beebeeb, BeebeebShare, BeebeebFileProvider) and the
BeebeebCrypto Pods target both compile the same file content. Earlier the
two paths held byte-identical copies that drifted silently on every
regen — that class of bug is gone.

> The Pods target and the Xcode native targets still each compile the
> Swift file (~160 KB) once per target. They live in distinct Swift
> modules (`BeebeebCrypto` vs `Beebeeb`/`BeebeebShare`/`BeebeebFileProvider`)
> so the duplicate symbols don't clash. Eliminating the per-target
> recompilation requires linking the BeebeebCrypto static framework into
> the extension targets and rewriting consumer code to
> `import BeebeebCrypto`; that's the structural follow-up described in
> 0431's spec and was scoped out of the initial dedup to keep the
> blast radius minimal during the May 2026 stabilization push.

## Regenerating the bindings

The bindings are produced by `repos/core/build-ios.sh`, which:

1. Builds the Rust `beebeeb-uniffi` crate for `aarch64-apple-ios`,
   `aarch64-apple-ios-sim`, and `x86_64-apple-ios`.
2. Lipo-merges the two simulator slices into a fat archive.
3. Strips debug + local symbols from both staticlibs.
4. Bundles the staticlibs + the `beebeeb_uniffiFFI` C header + modulemap
   into `repos/core/BeebeebCore.xcframework`.
5. Copies the freshly generated Swift bindings to
   `repos/core/BeebeebCore.swift`.

To sync the outputs into `repos/mobile/`:

```sh
cd /Users/guuslangelaar/Development/Beebeeb/beebeeb.io
./repos/core/build-ios.sh
rm -rf ./repos/mobile/ios/BeebeebCore.xcframework
cp -R ./repos/core/BeebeebCore.xcframework ./repos/mobile/ios/
cp ./repos/core/BeebeebCore.swift ./repos/mobile/modules/beebeeb-crypto/ios/beebeeb_uniffi.swift
# The symlink at ./repos/mobile/ios/Beebeeb/beebeeb_uniffi.swift picks
# up the new content automatically — do NOT also copy there.
```

After regen, rebuild the workspace and rerun the crypto sanity flow
(sign in, list photos, decrypt one). If any Swift consumer file
references a type/method that the new bindings removed (e.g. a
removed `DownloadProgressCallback`), the build will fail at compile
time pointing to the consumer site — fix the consumer, do NOT
hand-edit the bindings.

## Common drift symptoms

| Compile error | Likely cause |
|---|---|
| `cannot find type 'UniffiVTableCallbackInterface…' in scope` | The xcframework was rebuilt but the Swift bindings file wasn't replaced (or vice-versa). The C-side struct is missing in the modulemap header. Re-run `build-ios.sh` and re-copy both outputs. |
| `cannot find 'uniffi_beebeeb_uniffi_checksum_…' in scope` | Bindings expect a Rust function that no longer exists. Either re-add the function on the Rust side, OR regen the bindings + remove the Swift consumer that called it. |
| `cannot find type 'MasterKeyHandle' in scope` (from inside Pods build) | The pod's FRAMEWORK_SEARCH_PATHS lost the relative path to `BeebeebCore.xcframework`. Check `BeebeebCrypto.podspec` (`pod_target_xcconfig.HEADER_SEARCH_PATHS` and `OTHER_SWIFT_FLAGS`). |

## Why the duplicate file existed historically

Pre-0431, `ios/Beebeeb/beebeeb_uniffi.swift` was a real file (not a
symlink) that the Xcode project compiled into the `Beebeeb`,
`BeebeebShare`, and `BeebeebFileProvider` targets. The
`BeebeebCrypto` pod compiled the other physical copy at
`modules/beebeeb-crypto/ios/beebeeb_uniffi.swift`. Both files were
byte-for-byte identical (MD5 `45f75b0e303f312ba6dfbc06896e5803`
at the time of dedup) because the regen workflow always touched both
paths. A regen that touched only one would silently bit-rot the other.
The symlink eliminates that failure mode.
