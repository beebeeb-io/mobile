## Duplicate Runner Risk

Native camera-roll backup is active in the current app path. `BackupProvider` is mounted at `src/App.tsx:895`, startup/toggle/manual paths call native bridge functions at `src/lib/backup-context.tsx:188`, `src/lib/backup-context.tsx:260`, `src/lib/backup-context.tsx:361`, and `src/lib/backup-context.tsx:364`, and Swift starts `NativeBackupEngine` at `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:945` through `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:952` plus `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:986` through `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:998`.

The JS runner is present but not active in the current app tree. `PhotoBackupBridge` contains the JS startup, foreground, Wi-Fi-reconnect, force-trigger, and cleanup effects at `src/lib/PhotoBackupBridge.tsx:496` through `src/lib/PhotoBackupBridge.tsx:557` and `src/lib/PhotoBackupBridge.tsx:591` through `src/lib/PhotoBackupBridge.tsx:595`, but the current `src/App.tsx:895` through `src/App.tsx:1021` tree mounts `BackupProvider` without mounting `PhotoBackupBridge`.

JS and native camera-roll backup cannot both run from the current checked `src/App.tsx` tree because the JS bridge is not mounted there. They can both run in the same app session if `PhotoBackupBridge` is mounted inside the current provider tree: `BackupProvider` already starts native backup when `isPhotoBackupEnabled` is true at `src/lib/backup-context.tsx:223` and `src/lib/backup-context.tsx:188`, while `PhotoBackupBridge` would also start `PhotoSyncEngine` from the same `isPhotoBackupEnabled` state at `src/lib/PhotoBackupBridge.tsx:496` through `src/lib/PhotoBackupBridge.tsx:502`. Native foreground work stops cooperatively around the active Rust uploader, and source evidence does not prove that the active Rust upload uses background `URLSession`. `uploadSingleAsset` checks `isRunning` before asset fetch, key derivation, encryption, and the upload call at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:549` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:583`, then calls Rust `uploadEncryptedFile(...)` at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:585` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:599`. JS work can still continue until the current `encryptedUpload` resolves if `PhotoBackupBridge` is mounted. Cleanup aborts the controller at `src/lib/PhotoBackupBridge.tsx:518` through `src/lib/PhotoBackupBridge.tsx:525`, but `encryptedUpload` is called without a passed signal at `src/lib/PhotoBackupBridge.tsx:210` through `src/lib/PhotoBackupBridge.tsx:237`; the abort check happens only after the await returns at `src/lib/PhotoBackupBridge.tsx:238`.

## Progress Model Problems

Absolute counters are produced by native, then narrowed before RN stores them. Native `refreshProgress()` computes `totalAssets`, `completedAssets`, `failedAssets`, and `inProgressAssets` from SQLite at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:1094` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:1102`; `currentProgress()` returns those plus aggregate bytes and flags at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:250` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:262`; the TypeScript type exposes only `total`, `completed`, `inProgress`, and `lastBackupAt` at `modules/beebeeb-crypto/src/BeebeebCrypto.ts:673` through `modules/beebeeb-crypto/src/BeebeebCrypto.ts:678`; and `BackupProvider` stores only `total`, `completed`, and `inProgress` from the native poll at `src/lib/backup-context.tsx:232` through `src/lib/backup-context.tsx:240`.

Remaining counters are produced in the JS path from status-count snapshots rather than from the native progress model. `PhotoBackupBridge` computes `pending` from `pending_upload` plus `pending_reupload` at `src/lib/PhotoBackupBridge.tsx:263` through `src/lib/PhotoBackupBridge.tsx:268`, again after start-sync completion at `src/lib/PhotoBackupBridge.tsx:399` through `src/lib/PhotoBackupBridge.tsx:406`, and after manual reconciliation at `src/lib/PhotoBackupBridge.tsx:471` through `src/lib/PhotoBackupBridge.tsx:478`. The reminder notification also derives a remaining-photo count from pending rows at `src/lib/PhotoBackupBridge.tsx:567` through `src/lib/PhotoBackupBridge.tsx:577`. Native does not return a `pendingAssets` field from `currentProgress()` at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:250` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:262`.

Current file and current asset detail exist in pieces but are lost across the active native bridge. JS queue entries include `assetId`, `filename`, `sizeBytes`, `status`, and `progress` at `src/lib/backup-context.tsx:55` through `src/lib/backup-context.tsx:61`; `PhotoSyncEngine` initializes queue rows with local asset IDs at `src/services/PhotoSyncEngine.ts:167` through `src/services/PhotoSyncEngine.ts:177`, replaces filename and size after `MediaLibrary.getAssetInfoAsync` at `src/services/PhotoSyncEngine.ts:231` through `src/services/PhotoSyncEngine.ts:247`, and updates per-file upload percent at `src/services/PhotoSyncEngine.ts:281` through `src/services/PhotoSyncEngine.ts:289`. JS upload progress also reports `currentFileName`, bytes, and chunk counters at `src/lib/PhotoBackupBridge.tsx:228` through `src/lib/PhotoBackupBridge.tsx:234`. Native has `onFileStatus` with asset ID, status, filename, and error at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:141` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:143`, sends `"uploading"` with no filename at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:545` and `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:546`, sends `"uploaded"` with a generated filename at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:609`, and sends failures with no filename at `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:679` through `modules/beebeeb-crypto/ios/NativeBackupEngine.swift:686`; however, `BeebeebCryptoModule` exposes native progress only through `getBackupProgress`, `getNativeBackupProgress`, and batch-return dictionaries at `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:982` through `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:984` and `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:1093` through `modules/beebeeb-crypto/ios/BeebeebCryptoModule.swift:1102`, so current asset, current filename, and current per-file byte counters are not delivered to `BackupProvider`.
